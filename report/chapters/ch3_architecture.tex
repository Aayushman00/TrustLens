\section{Implemented system versus target design}
The repository README contains a long target architecture: a model analyzer, a dataset analyzer, a resource checker, a benchmark-first runtime estimate, user confirmation and then the FRIES evaluation. When we read the source we found that part of that diagram runs and part does not. This chapter describes the \emph{implemented} flow and lists the differences in Table~\ref{tab:impl-status}, because a report that drew the target diagram as if it ran would misdescribe the project.

The API process validates requests, stores model records and evaluation drafts, and enqueues a Celery task. The worker loads the model through the inference backend, runs the probes, stores raw evidence, asks the O/S/D engine for ratings, calls the scorer and writes everything back to PostgreSQL. The browser reads the finished evaluation and its report. Since round~3 (L8) the API commits the request session \emph{before} it sends the Celery message. Earlier, the worker could pick up a task for an evaluation row that the API had not committed yet, and we had seen evaluations stay in \code{PENDING} for that reason.

\section{Data flow and evaluation contract}
Each evaluation carries an \emph{evaluation contract} (schema \code{v2} in \code{schemas/\allowbreak evaluation\_contract\_v2.py}) that makes the evaluation explicit. For Fairness and Robustness it records the content-addressed dataset, the text and target columns, the sensitive-attribute column, a \code{label\_mapping} from dataset values to model label indices, \code{min\_group\_n} and the \code{positive\_label\_index} that the fairness metrics treat as the favourable outcome. It also freezes a snapshot of the model's \code{id2label} and the resolved model revision. The contract turned out to matter: in our first experiment it made a label-mapping mistake visible after the fact (Section~\ref{sec:pilot}).

\section{Evaluation modes and assessment engines}
Two orthogonal switches control an evaluation.

\textbf{Workflow mode.} \code{AI\_AUTONOMOUS} lets the pipeline finalise without a reviewer (the report is marked \code{human\_reviewed=false}); \code{AI\_ASSISTED} stops so that a reviewer can edit O/S/D before the score is computed. Despite the enum names, no language model is involved in the mode itself; the two are human-review gates.

\textbf{Assessment engine.} Three engines are implemented.
\begin{description}[leftmargin=1.2em]
\item[\code{deterministic}] (default) never proposes O/S/D; the FRIES score is withheld unless a human supplies the ratings.
\item[\code{legacy\_heuristic}] maps probe metrics to O/S/D with documented rules (Section~\ref{sec:osd}).
\item[\code{llm\_v1}] starts from the heuristic proposal and then asks an LLM to re-rate Integrity, Explainability and Safety. Fairness and Robustness always keep the heuristic ratings, and when behavioural Safety evidence exists the Safety band is also kept from the heuristic; the LLM judgment is stored as metadata.
\end{description}
The experiments in this report use \code{llm\_v1} in \code{AI\_AUTONOMOUS} mode unless a section says otherwise. That is why repeated runs can differ in the LLM-rated dimensions (Section~\ref{sec:repeat}).

\section{Evidence statuses and abstention}
A probe does not always produce a number. The implemented statuses are \code{EVALUATED}, \code{PROXY}, \code{SKIPPED}, \code{NOT\_APPLICABLE}, \code{INSUFFICIENT\_EVIDENCE} and \code{FAILED}. On top of the status, each dimension records an \code{aspect\_scoring} outcome: \code{risk\_detected}, \code{no\_material\_risk}, \code{disparity\_observed}, \code{disclosure\_gap}, \code{mapping\_blocked} or \code{not\_scored}. The O/S/D engine abstains (returns \code{None}) wherever the status or \code{aspect\_scoring} says the evidence is not enough, and the report builder withholds the overall FRIES score when any dimension lacks a complete O/S/D triple. The API answers a report request for such an evaluation with HTTP~409 rather than pretending the report is merely not ready yet.
